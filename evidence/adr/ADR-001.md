# ADR-001 — Tablekeeper service architecture

- Status: accepted (stage 1); binding on stages 2–4 unless superseded by a later ADR
- Author: Builder
- Context: Tablekeeper stage-1 specification (§1–§11); later stages add a browser UI (stage 2), dated
  policies, history and recurring series (stage 3) and a constrained seating optimiser (stage 4) on the
  same state.

## 1. Runtime and language — Go 1.26

Decision: Go, standard library first. The service is one statically linked binary.

Why:
- **Time zones.** `time.LoadLocation` with the `time/tzdata` package embedded in the binary gives the full
  IANA database with no files in the image and no runtime network (§2, §9). DST resolution (skipped
  hour → `invalid_local_time`, repeated hour → first occurrence, absolute-time durations) is done
  explicitly on top of `time.Location`, not left to `time.Date`'s unspecified choice in ambiguous hours.
- **Concurrency.** `net/http` serves every request on its own goroutine; 50 in flight is trivial. A single
  `sync.RWMutex` around the state gives the serialisation in §4 below without a database.
- **Boot and footprint.** Start to healthy is milliseconds (limit 60 s); idle memory is a few MiB
  (limit 2 GiB); CPU-bound work (bcrypt) parallelises over both vCPUs.
- **Offline runtime.** Every dependency is compiled in. The only third-party module,
  `golang.org/x/crypto` (bcrypt), is vendored in the repository, so even `docker build` needs only the
  base images.
- **Later stages.** Stage 2's UI assets are embedded with `embed.FS` (fonts, scripts, styles — no CDN).
  Stage 3/4 logic (policies, series, optimiser) is plain Go over the same in-memory model.

## 2. Framework — `net/http` with a small dispatch layer

Decision: no web framework. Routes are registered on `http.ServeMux` by path; each route dispatches on
method itself so that every miss is our own JSON envelope (§5): unknown path → 404 `not_found`, known path
with wrong method → 405 `method_not_allowed`. A recovery middleware turns any panic into a 500 envelope
(and is a bug to fix — §5 forbids 5xx).

Request bodies are read with a size cap, decoded with `json.Decoder.UseNumber()` into
`map[string]json.RawMessage` (non-object, empty, trailing data or unparseable → 400 `malformed_request`),
then fields are read through typed accessors that distinguish *absent* (→ 422 `validation_failed` for a
required field), *wrong JSON type* (→ 400 `malformed_request`, except where an endpoint overrides, e.g.
`party_size` → 422) and *bad value* (→ 422). Unknown fields are ignored. A JSON `null` is treated as
*absent* (open point; follows any Foreman ruling).

Responses: `application/json; charset=utf-8`, HTML escaping off, timestamps formatted
`2006-01-02T15:04:05-07:00` (explicit offset, `+00:00` never `Z`).

## 3. Storage — in-memory state, one owner

Decision: all state lives in one Go value (`state.State`) in process memory. No database, no files.

Why: §2 says disk is ephemeral and state need not survive a restart; reset/import replace state
wholesale; export must be an atomic snapshot. A single in-memory value makes all three a pointer swap
or a serialisation under a lock, and keeps the model easy to snapshot for later stages.

The state holds: users (id, email, display name, bcrypt hash), tokens (token → user id), restaurants
with tables and opening hours in fixture order, reservations (id, reference, owner, restaurant, table,
party size, status, local start, absolute start/end, created_at), idempotency receipts, and counters for
generated ids.

## 4. Serialising writes

Decision: one process-wide `sync.RWMutex` (`state.Store`).

- Every state-changing operation — booking, cancel, amend, multi-booking move, signup insert, token
  issue — runs as a single critical section holding the **write lock**: resolve idempotency → validate
  against current state → check occupancy/cutoff → write → build the response → store the receipt →
  unlock. No request can observe or interleave with a half-applied change, so two overlapping
  `confirmed` bookings on one table cannot both commit, and a multi-booking move either applies all its
  changes or none (it computes the full resulting set first, checks it, then writes).
- Pure reads (`GET` endpoints, export) hold the **read lock** and therefore see a consistent snapshot.
- Expensive work never runs under the lock: bcrypt hashing for signup and fixture users happens before
  taking it (fixture users are hashed in parallel); login reads the hash under the read lock and compares
  outside it.
- Reset and import build and validate the complete new state *outside* the lock and then swap it in
  under the write lock, so a rejected import leaves the destination untouched and an accepted one is
  atomic.

Idempotency (§7, §11): receipts are keyed by `(user id, method, path, Idempotency-Key)`. A receipt stores
the canonical form of the request body (parsed JSON re-encoded with sorted keys and numbers normalised, so
key order, whitespace and `4` vs `4.0` do not matter), the original status and the original response
bytes. Lookup and store happen inside the same write-locked section as the operation, so of N concurrent
identical requests with a fresh key exactly one executes and returns 201; the rest find the receipt and
return 200 with the identical body. Only successful (2xx) results are stored, so a key whose first use
failed with 4xx stays usable. A receipt is never updated by later changes to the resource.

## 5. Startup in the container

Multi-stage `Dockerfile`: `golang:1.26-alpine` builds with `CGO_ENABLED=0 -mod=vendor -trimpath`; the
runtime stage is `alpine:3.22` with only the binary, running as a non-root user. The process reads
`PORT` (default `8080`), listens on `0.0.0.0:$PORT`, and serves `GET /health` → 200 `{"status":"ok"}` as
soon as the listener is up (the store is ready at construction). `RUN.md` gives the one-line build and run.

## 6. Export / import and versioning across stages

Export (`GET /_test/export`) serialises the state under the read lock:

```json
{ "track": "tablekeeper", "format_version": 1, "state": { "schema": 1, ... } }
```

- `format_version` is the envelope version the specification requires; `state.schema` is our own
  internal schema number, bumped whenever a later stage changes the state shape.
- Import validates `track`, `format_version` and the state, migrates it step by step
  (`schema 1 → 2 → … → current`) and only then swaps it in. **Every later stage keeps the decoders and
  migrations for every earlier schema**, so a stage-1 export imports into stage 2, 3 and 4 unchanged.
- The state carries everything needed for continuity: users with password hashes, live tokens,
  restaurants and tables, reservations with original ids, references, statuses and timestamps (never
  regenerated), idempotency receipts with canonical bodies and the original response bytes, and the id
  counters, so newly generated ids never collide with imported ones.
- Import is replacement, not merge; repeating it yields the same state. Missing fields, wrong
  track/version or a state that fails validation → 422 `validation_failed` with the destination unchanged.

## 7. Consequences

- Single-process, single-lock design caps write throughput at one operation at a time; at this workload
  (≤50 in flight, sub-millisecond critical sections) that is not a constraint, and it makes correctness
  arguments local.
- State is lost on container restart, which §2 allows.
- The Stylist works in the same Go module (time/DST and availability engine as its own package).
