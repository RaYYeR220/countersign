# ADR-002 — Stage 2: embedded browser UI, combined tables, state schema 2

- Status: accepted (stage 2); extends ADR-001, which still holds
- Author: Builder
- Context: the stage-2 specification adds a browser product (`/`, `/signup`, `/login`, `/lookup`), combinable
  table pairs (`table_ids`, `available_options`), and the requirement that a stage-2 service accept an export
  of the same team's stage-1 service with sessions, references and retries intact.

## 1. Serving the UI from the same binary

Decision: the UI is static HTML, CSS and JavaScript in `stage-2/internal/web/static/`, compiled into the
binary with `//go:embed` (`embed.FS`). It is served by the same `net/http` server and process as the API.
There is no second server, no build step that fetches packages, and no file read at run time.

- **Routes.** `GET`/`HEAD` on `/`, `/signup`, `/login` and `/lookup` return the HTML shell
  (`text/html; charset=utf-8`). Every other screen is reached through the UI. Assets are served under
  `/assets/{name}` with an explicit content type. Each route has an explicit `ServeMux` pattern, so every
  other unknown path still gets the §5 JSON 404 envelope. The API routes and the stage-1 JSON conventions
  are unchanged; §3.4's JSON convention does not govern the screen routes.
- **No runtime network.** No CDN, web font, analytics or remote script is referenced. Typography uses a
  system font stack. Icons and illustrations, if any, are inline SVG or CSS. The web package must carry a
  unit test (owner: Stylist) that scans the embedded
  files for `http://`/`https://` references to other origins. The image therefore renders identically with
  `--network none`.
- **Headers.** `Cache-Control: no-cache` on the shell and assets, so an upgraded image never serves a stale
  script against a newer API. `X-Content-Type-Options: nosniff` is set.
- **Client state.** The browser keeps the bearer token and the pending booking's retry identity
  (Idempotency-Key + exact body) in memory, or in `sessionStorage` where a screen change within the page must
  keep it. The server stays authoritative: a confirmation is shown only from a server response, including a
  replayed 200 from §7. Because the import keeps tokens and receipts (§3), a browser that was signed in
  before an export → import upgrade stays signed in, and its pending retry replays to the original
  confirmation.

Why: one artefact to build and start (§2), and nothing to fetch at run time. The UI is independent of the
core, because it uses only the public HTTP API.

## 2. Combined tables in the core

- `Reservation.TableIDs []string` replaces `TableID`. It holds one table, or a declared pair stored in
  `combinable` order, so responses, availability options and UI test ids all agree on order.
- `Restaurant.Combinable [][]string` holds the declared unordered pairs in fixture order. An absent list is
  stored and served as `[]`.
- Occupancy: two confirmed reservations conflict when their table sets share a member and their half-open
  intervals overlap (`state.SharesTable` + `TableBusy`). Booking, amendment and moves still run as one
  write-locked plan → check → apply step (ADR-001 §4). So of two concurrent pair bookings that share a table,
  exactly one commits.
- Requests accept `table_id` (a set of one) or `table_ids`. Responses always carry `table_ids` and carry
  `table_id` only for a single table. `available_table_ids` remains singles only; `available_options` lists
  singles in fixture order, then pairs in `combinable` order, with summed capacity.

## 3. State schema 2 and the stage-1 → stage-2 migration

The export envelope stays `{"track":"tablekeeper","format_version":1,"state":{…}}`. Our own
`state.schema` moves from 1 to 2. Import reads every schema from 1 up to the current one and migrates it
one step at a time (`snapshot.migrations`), before the usual decode and integrity check (`state.Rebuild`).

`schema1to2`:
- each reservation's `"table_id": X` becomes `"table_ids": [X]`;
- each restaurant without `combinable` gains `"combinable": []`;
- users and password hashes, tokens, reservation ids, references, statuses and all timestamps are carried
  over unchanged. Idempotency receipts (key → canonical body, status, original response bytes) are carried
  over unchanged too, so a stage-1 retry replays its original stage-1 response byte for byte, and a key
  whose first use failed is still a first use.

Evidence that this reads the real stage-1 format, not our assumption of it:
`stage-2/internal/snapshot/testdata/stage1-export.json` was exported by the accepted stage-1 service (a
seeded booking since cancelled, a booking with key `book-1` moved with key `move-1`, and a failed key).
`TestImportStage1Export` and `TestUpgradeFromStage1Export` import it and check sessions, lookups, both
replays (byte-identical), key reuse, the failed key, and a schema-2 re-export round trip.

Rule for later stages (unchanged from ADR-001 §6): never remove a migration; add `schema N → N+1` whenever
the persisted shape changes, and keep a real export of every earlier stage as test data.
